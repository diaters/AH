# 单通道用户任务、受管进程与持续监控通知修正规格

> __状态：活跃规格，用户已确认，实施中。__
> 2026-10-28 用户确认书面规格；实现与验证按配套计划分批推进，尚未宣称全部完成。
> 当前实现以 [current-state.md](../../current-state.md) 为准。

## 1. 背景与评审范围

本稿基于主线 `a15e1187517d781dceb6067703275e5aacce924b`。
触发事件为 `harness_2026-10-28_21-54-03.jsonl` 中的 22 端口监控与执行中追问。
该日志运行未使用主线已经合入的 steer 链路；后续核验区分了旧版本行为与主线仍有的缺口。

主线核验结果：

- `loop_steering_flow` 六项集成测试通过，包括 steer 注入、停止在飞请求和后台退出通知。
- native backend 九项单元测试通过，包括超时终止进程组和输出读取宽限。
- 临时诊断复现三处缺口：释放 backend clone 误杀共享会话、已返回的 `shell_exec`
  遗留后台进程、持有 backend 的宿主被强杀后会话仍存活。
- 后台通知只检测会话退出；持续输出不会触发通知。
- 普通输入优先选择空闲任务，存在同通道多任务歧义。

本稿将修正拆成四个可独立评审的变更：

- 进程所有权与一次性执行回收。
- Harness 异常死亡后的独立收尾。
- 单通道用户任务唯一性与 steer 路由。
- 持续监控事件、发送结果与任务唤醒联动。

## 2. 用户已确认的约束

- 同一个 `ChannelId` 只允许一个未结束的顶层用户任务。
- 普通消息始终进入该任务；执行中走 steer，等待用户时续轮。
- 旧任务结束并完成后台资源清理后，下一条消息才能创建新任务。
- 内部子任务仍可并行，不占通道用户任务名额。
- 定时任务只向通道输出，不占用户会话名额，不接收该通道的普通聊天输入。
- `/stop` 中断回合并保留任务；`/finish` 结束任务；旧任务未结束时 `/btw` 不创建新任务。
- Harness 退出或异常死亡后，此实例启动的受管监控脚本应随之被清理。

通道采用现有 `ChannelId` 的完整身份，不另按 Agent、Task 更新时间或消息发送者分配名额。
群聊审批仍沿用发起人绑定规则，输入归属与审批权限各自遵循现有边界。

## 3. 单通道用户任务

### 3.1 约束对象

用户会话顶层任务满足 `origin_channel.is_some()` 且 `parent_task_id.is_none()`。
定时与事件任务的 `output_channel` 只表示投递目标，不能用来判定它们占用用户会话名额。

历史终态任务可以保留在 ECS 中；限制针对未结束任务及尚未完成资源回收的关闭中任务。
不引入“当前任务选择器”或可自动切换的焦点。

### 3.2 输入规则

| 现有任务情况 | 普通输入处理 |
| --- | --- |
| 没有占用通道的任务 | 第一条输入创建任务，后续输入进入它 |
| `Pending`、`Ready`、执行中或等待工具、Agent、子任务 | 投递 `TaskInbox`，下一次请求前消费 |
| `Waiting(User)` 且无审批请求 | 走既有 `ContinueTaskMessage` |
| 等待工具审批 | 走既有审批回复解析，不创建任务 |
| `Waiting(AskUser)` | 返回 `ask_user` 工具结果，不创建任务 |
| 已进入终态但仍在清理 | 输入保留在入向队列，清理确认后再处理 |

steer 继续复用 `InboxDeliveryMessage`、`context_attachment_system` 和 `inbox_wake_system`。
同一条输入只消费一次，写入 STM，并进入实际发送的工具循环对话。

### 3.3 创建入口与同帧竞态

唯一性由用户任务创建入口保证，路由层只负责选择动作：

- 用户任务创建统一经过 `CreateTaskMessage` 的收口入口；命令与插件不得直接绕过。
- 每个创建批次先读取占用情况，处理第一条创建请求后立即在批次中保留该通道名额。
  Bevy `Commands` 延迟落地期间，后续请求也能看到该保留结果。
- ingress 分配单调输入序号，批次按该序号处理；序号仅供内部排序，不暴露给 LLM。
- 通道已有任务时，重复的用户创建请求转为对该任务的输入，不生成第二个 Task。
- 创建实体、更新 `EntityIndex`、投递收件箱之间设置明确的系统顺序与 deferred 同步点。
- 已有多任务异常状态不按 `first()` 静默选取：记录不变量错误并提示结束多余任务。
  当前 Task 不跨进程持久恢复，本次不引入自动合并历史任务的算法。

先以批次内保留和既有 ECS 查询实现约束；不新增独立的会话实体或第二份持久任务账本。

### 3.4 命令与结束边界

- `/stop` 保留任务和通道名额，取消当前回合的在飞执行，沿用既有回合代次作废机制。
- `/finish` 结束唯一用户任务，取消所属未完成子任务、在飞执行及受管后台会话。
- `/clear` 同样先执行资源清理，再删除任务实体并释放名额。
- `/btw` 在通道被占用时返回“当前任务未结束，请先 /finish”；不隐式结束旧任务。
  通道空闲时允许按主题文本创建一个新任务。
- 自动空闲结束与重试耗尽产生的终态同样经过清理流程。
- 普通文本回复进入 `Waiting(User)`，不等同于任务结束。

关闭中的新输入不写入旧任务的 STM，也不提前派发新任务。
清理失败时保留通道占用并显示失败原因，不能宣称旧任务已完全释放。

## 4. 进程所有权与执行契约

### 4.1 backend 的共享句柄

`NativeProcessBackend` 的 clone 只克隆共享管理器的引用；外层句柄不实现杀进程的 `Drop`。
进程、进程组、取消信号与归属统一由管理器持有。

主运行时显式调用幂等 `shutdown()`：先拒绝新启动，再取消执行、停止进程组、等待回收，
最后停止进程管理服务。共享内部状态的最终析构仅作遗漏路径的兜底。
worker 持有的 clone 不决定主运行时何时关闭。

`OwnedToolContext.current_task_id` 已存在，`shell_exec` 必须使用它，不能继续写入 nil。
Agent 归属从 dispatch 现场明确传递，不另建可由模型修改的所有权参数。

### 4.2 两种生命周期

| 模式 | 存活范围 | 回收条件 |
| --- | --- | --- |
| `shell_exec` | 本次工具执行 | 命令返回、取消、超时、所属任务结束或 Harness 关闭 |
| `shell_start` | 受管会话，可跨回合 | `shell_stop`、所属任务结束或 Harness 关闭 |

所有实际进程从启动前的登记到最终回收都可追踪，不能只登记 `shell_start`。
一次性命令的主 shell 正常返回时，也清理留在该进程组中的后台后代，再完成工具结果。
输出读取使用现有有界缓冲和退出宽限，避免后代持有管道导致无限等待。

停止流程先发送终止信号，等待最多一秒，再强杀残留进程并执行退出状态回收。
单个进程失败不阻止其他会话继续清理；失败按任务和会话身份记录。

## 5. Harness 异常死亡保障

### 5.1 方案比较

| 方案 | 正常退出 | Harness 被强杀 | 结论 |
| --- | --- | --- | --- |
| 脚本自己检查父进程 | 依赖生成脚本 | 存在轮询与身份判断问题 | 不作统一保障 |
| 进程内注册表与析构 | 可覆盖正常收尾 | 清理代码无法执行 | 作为正常路径 |
| 实例级独立进程守护器 | 主动关闭 | 检测存活连接断开后清理 | 本稿采用 |

### 5.2 守护器边界

每个 Harness 实例启动一个轻量守护进程。它属于进程 backend，不参与 Brain、WorkItem
或 Agent 调度，不作为长期系统服务安装。可复用同一可执行文件的内部入口。

```text
Harness 主运行时
  -> backend 请求接口
    -> 实例级进程守护器
      -> 执行 A 的独立进程组
      -> 执行 B 的独立进程组
```

- 守护器实际创建命令，先登记归属再确认启动，覆盖“启动后、登记前 Harness 死亡”的窗口。
- 守护器与命令各自使用独立进程组，避免前台终端信号同时终止守护器和 Harness。
- 专用存活连接由 Harness 持有；工作命令关闭无关描述符，不继承存活连接。
- 正常关闭复用停止全部进程的协议；异常关闭由连接 EOF 触发相同回收流程。
- 连接失效后不再执行缓冲中的新启动请求；已创建但尚未回传的执行也必须回收。
- 进程组 ID 只在执行存活范围内使用；不能跨实例使用持久 PID 文件猜测身份。
- 守护器意外退出时，Harness 停止接受进程工具并明确报告服务故障，不静默降级。

保障范围为受管命令及留在其进程组中的后代，覆盖普通 `&` 和 `nohup`。
主动通过 `setsid` 或外部服务管理器脱离进程组的 daemon 不在此保障范围内；
本次监控脚本采用前台方式运行。绝对约束任意主动脱离的程序需要系统级隔离，应另行评审。

首次实现与强杀验收覆盖当前项目的 Unix 平台：macOS、Linux，Android 做构建与设备回归。
其他平台不能在缺少对应保障时宣称支持该生命周期承诺。

集成测试显式使用构建出的 Harness 可执行文件启动内部守护入口；入口不加载 LLM、通道或 TUI。

## 6. 持续监控事件与通知

### 6.1 对外工具面

保留六个 shell 工具。`shell_start` 新增 `notify_on_output: bool`，默认 `false`；
`notify_on_exit` 保持现有默认 `true`。

启用 `notify_on_output` 表示 stdout 中每条完整行是调用方选择推送的监控事件：

- 脚本自行筛选业务事件，并及时刷新完整行；普通调试信息写 stderr。
- 输出事件经 Harness 的任务输出通道发送，并以后台通知进入所属 `TaskInbox`。
- 脚本不接触 QQ 凭据，也不自行调用消息平台接口。
- `shell_read` 仍返回最新快照；事件序号、确认位置与重试状态仅在 backend 内部维护。
- 工具审批摘要展示此开关及目标通道；工具描述明确“启用后 stdout 会发送给用户”。

### 6.2 本稿新增的设计选择

为使“马上告诉我”不依赖一次额外 LLM 请求，本稿采用 __Harness 先投递告警，Agent 接收上下文通知__：

```text
受管脚本的完整事件行
  -> 有界事件队列与合并
    -> 现有 ChannelManager 出向路径 -> 平台发送结果
    -> TaskInbox -> 既有注入或空闲唤醒链路
```

这是对前期“先唤醒 Agent，再由 Agent 调用 channel_send”的细化，需随本稿评审。
事件文本已由用户授权启动的脚本筛选，Harness 负责确定性转发；
Agent 可解释、总结及响应用户 steer。初始通知标为“排队中”，平台回执再报告“送达”或“失败”；
Agent 不得把排队复述为送达，也无需再次原样转发已由 Harness 负责投递的事件。

后台内容按 `TaskNotification` 送达，不能伪装为用户 steer，也不登记为可信图片来源。

### 6.3 合并、背压与送达结果

- 每个事件具有内部身份 `(session_id, sequence)`，消费确认不使用输出快照差分。
- 正常合并窗口沿用 300 毫秒，从本批第一条事件计时，到期即发送；持续新事件不延长截止时间。
  按事件顺序合并成消息，超过单批上限时拆分为后续批次。
- 单事件不超过现有 64 KiB 输出快照上限；超长单行保留尾部，并标注原字节数与截断事实。
- 每会话待处理事件缓冲上限为 1 MiB；溢出时停止该监控会话并报告可见错误，不能静默丢失。
- `ChannelManager` 的入队成功与平台发送成功分开记录，统一回送内部发送结果。
- 同进程内发送失败采用有界退避：一秒、两秒、四秒，三次重试后标记失败，保留失败记录供查询。
- 平台支持幂等键时复用内部消息身份；不支持时承认重试可能重复，不能承诺恰好一次。
- 无事件时不发送“无变化”、空消息或占位标记。
- 本次不承诺跨 Harness 重启恢复未送达事件；关闭时停止监控并记录仍未送达的数量。

任务结束后拒绝新事件；尚未排入通道的事件转为终止记录，最终回执携带其数量。
已经排入通道的消息可能稍后送达，仍携带旧 Task 身份，结果只记录到原任务，不能唤醒新任务。

定时任务继续使用独立执行与输出策略，不转为占用用户会话的常驻任务。

### 6.4 Agent 唤醒与空闲结束

- `Waiting(BackgroundJobs)` 可以被已入箱的输出事件或用户 steer 唤醒，后台进程继续存活。
  “所有后台任务结束”只作为自然完成的门槛，不能作为消费每条事件的门槛。
- 用户 steer 立即参与下一次请求，不消耗后台自动唤醒额度。
- 后台自动唤醒改为滚动窗口限流：默认每十秒五轮。超限时合并积压，窗口恢复后自动处理，
  不再永久等待下一条用户输入。
- Agent 侧通知合并同样以首条积压的时间确定截止，持续收到新事件不能无限推迟处理。
- `HARNESS_MAX_AUTO_WAKES` 保留名称，语义改为窗口额度；新增
  `HARNESS_AUTO_WAKE_WINDOW_SECS`，默认 `10`，随实现更新配置与示例。
- 告警投递不受 Agent 唤醒额度限制；模型忙碌时告警照常发送，上下文稍后注入。
- 存在真实受管会话、在飞工具、未处理通知或未完成子任务时，不执行会话空闲自动结束。
  活跃资源以 backend 与既有执行状态为准，不能只检查通知用的 `OwnedJobs`。

## 7. 错误处理与观测

复用现有结构化日志，新增事件至少包含 `task_id`、适用时的 `session_id` 和执行身份：

- 通道任务占用冲突、重复创建转投递、关闭期间输入延期。
- 进程启动登记、进程组停止、强杀升级、回收完成与失败。
- 守护器启动、存活连接断开、异常退出与故障后拒绝启动。
- 输出事件入队、合并、限流延期、缓冲溢出。
- 通知排队、平台送达、重试与最终失败。

启动日志增加构建提交标识，方便区分“已合入源码”与“实际运行二进制”。
通知延迟分别记录检测、排队与通道发送阶段，避免把轮询检测称为零延迟实时检测。

## 9. 验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同通道同帧收到十条输入 | 一个用户 Task，十条输入有序保留，不重复派发 |
| 原任务执行中输入补充要求 | 原 Task 的下一次真实请求包含 steer，STM 与工具对话一致 |
| 通道有内部并行子任务及定时输出 | 不创建第二个用户顶层任务，输入不进入定时任务 |
| `/btw`、`/stop`、`/finish` | 分别拒绝并行新建、保留原任务、清理后开放新建 |
| 结束与新输入同帧发生 | 新输入不丢失，资源回收确认前不派发新任务 |
| 释放任意 backend clone | 其他受管会话继续运行 |
| `shell_exec` 返回但留下 `nohup sleep` | 返回工具结果前收回该进程组的残留 |
| 正常退出、panic unwind、进程 abort、SIGKILL | 守护器收回受管进程及普通后代，五秒内确认无运行残留 |
| 启动登记与 Harness 关闭竞争 | 不出现未登记且仍存活的命令 |
| 连续第六、第十个监控事件 | 告警均可投递，Agent 自动处理可限流但会恢复 |
| 监控脚本仍运行但产生输出 | 用户收到告警；Agent 能消费通知，脚本继续运行 |
| 静默监控超过会话空闲阈值 | 任务与监控不被自动结束 |
| 通道暂时失败或事件缓冲溢出 | 有重试或明确失败记录，不冒充成功、不静默丢失 |
| 连续输出、超长单行及结束后的迟到回执 | 合并窗口按时到期，截断有提示，迟到结果不唤醒新任务 |
| 模型与 QQ 的真实端口监控场景 | 启动回执、连接告警、steer 调整及退出清理全部可验证 |

端口传感脚本单独验证入站方向、IPv4/IPv6、短连接与重连。
未经过该验证时，不能仅用五秒一次的连接快照宣称能捕获所有连接。

## 10. 评审前自检

- 已区分用户确认的任务边界与本稿待评审的进程、通知实现选择。
- 没有把顶层用户任务限制扩展到内部子任务、WorkItem 或定时输出任务。
- 没有把 `Waiting(User)`、`/stop` 或普通文本回复当作任务结束。
- 所有进程停止路径共用 backend，异常死亡收尾在 Harness 进程之外。
- 持续输出复用原有收件箱、注入及通道，不新增端口专用工具或 Agent 调度循环。
- 告警直投与 Agent 后续处理的区别、发送失败及平台边界已写明。
- 当前实现状态未被误标为完成；实施前需书面评审。

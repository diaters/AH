# ADR-002: Agent 受控演化模型

## 状态

Accepted

## 生效范围

本决策自 2026-05-17 起生效，关联设计文档：

- Phase 3 多 Agent 设计（`docs/design/2026-05-16-multi-agent-design.md`）
- Phase 4.2 Tool 与 Space 设计（`docs/design/2026-05-17-tool-space-design.md`）

## 背景

Phase 3 多 Agent 设计中，Agent 被定义为"不可变配置实体"。该定义有助于把执行状态收敛到 `Task`，避免 `Agent` 重新演变为 `Idle/Busy` 状态机实体。

但随着 Phase 4.2 Tool、权限与审批链设计推进，单纯的"不可变配置"已经无法完整表达以下需求：

1. Agent 需要持有长期有效的 Tool 权限配置
2. Agent 需要在用户授权或父 Agent 审批后修正长期权限
3. Agent 需要沉淀执行经验，形成可复用的长期记忆
4. Agent 需要具备有限的自我进化能力，而不只是被动执行静态配置

如果继续坚持 Agent 完全不可变，会出现两个问题：

- 长期有效的执行配置只能被迫塞进 `Task` 或全局 Resource，导致职责漂移
- Agent 的经验积累与权限修正无法形成稳定归属，后续难以支持继承、持久化和审计

另一方面，如果直接允许 Agent 持有所有运行时状态，又会破坏当前项目已经建立的 ECS 主链路边界，导致：

- `Task` 与 `Agent` 的职责重叠
- 异步执行过程直接改写 `World`
- 审批、重试、多轮对话等状态散落在多个实体中

因此需要一个中间方案：允许 Agent 受控演化，但不让 Agent 承担瞬时执行状态。

## 决策

将 Agent 的定位从"不可变配置实体"修订为"可演化的执行配置实体"。

具体决策如下：

1. Agent 仍然主要描述"如何执行"，而不是"当前执行到哪里"
2. Agent 不承载 `Idle`、`Busy`、`Running`、`Waiting`、`RetryBackoff` 等瞬时运行状态
3. Agent 允许持有长期有效、可继承、可审计的执行配置
4. Agent 允许在运行期间通过受控机制修正部分长期配置
5. 所有修正必须通过 ECS 内显式 message / system 完成，不能由异步 future 直接修改 `World`

允许运行期修正的内容包括：

- Tool 权限配置
- Agent 经验记忆
- 偏好化执行策略
- 可继承的长期约束

明确禁止运行期直接写入 Agent 的内容包括：

- 当前是否正在执行
- 某次调用的中间结果
- 某个任务是否等待审批
- 某次重试的退避状态
- 某个多轮会话的短期上下文

这些内容继续由 `Task`、`ShortTermMemory` 和一次性 `Message` 承担。

同时约束：

1. 权限扩张必须经过用户确认或父 Agent 审批
2. Agent 的演化结果应当可追踪，必要时支持持久化
3. `tags` 继续表达能力范围与匹配边界
4. `tool_permissions` 单独表达可执行操作权限，不能替代 `tags`

## 后果

__正面__：

- Agent 的长期配置、权限和经验拥有清晰归属
- 为 Tool 权限继承、父 Agent 审批、自我进化提供统一模型
- 保留 `Task` 作为执行态核心对象，避免状态分散
- 后续可以自然扩展 Agent 演化结果的持久化和审计

__负面__：

- `Agent` 结构会扩张，需要新增 `tool_permissions`、`experience` 等字段
- Phase 3 文档中的"不可变配置实体"表述需要同步修订
- 需要额外定义哪些字段允许修正、哪些字段禁止修正，避免边界再次模糊
- 若未来引入配置持久化，需要额外设计"运行时修正如何写回"的策略

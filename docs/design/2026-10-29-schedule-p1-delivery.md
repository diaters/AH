# 定时监控 P1 交付契约

> __状态：当前有效__ — 实现已确认的无人值守定时任务设计 P1，P2 探针与 P3 任务级授权另行推进。

## 运行与通知

- `ScheduleDefinition.notify` 默认为 `reply`，最终回复经 `ChannelManager::send_with_result`
  返回平台真实发送结果；`explicit` 最终回复仅 TUI 可见，需要通知时显式调用 `channel_send`。
- 两种策略的 `channel_send` 都纳入实际发送回执统计。入队成功不计通知成功，任一发送失败
  将该运行记为 `Failed`，保留已成功的通知数量；回执未结束时不提交最终运行记录。
- 每次触发创建独立运行，保存触发时间、完成时间、结果、错误摘要、结果摘要与业务通知数量。
  `Notified` / `Silent` / `Failed` 为执行结果，重叠跳过和过期错过分别记
  `SkippedOverlap` / `Missed`，不增加连续失败次数。暂停的定时器不会创建运行。
- 定时任务的状态变化只在 TUI 展示。失败、补跑、阈值告警和恢复使用已有系统通知通道。
  系统通知与业务通知分别处理；业务通知数量不把系统告警入队当成平台发送成功。

## 持久提交与恢复

- 每个 schedule 的 `runs.jsonl` 与 `state/` 分离。Harness 单写者先验证已有账本，
  按任务 ID 或未执行触发的时间与结果去重，再追加并同步；统计也对已有重复记录去重。
- 损坏记录、截断尾部与 I/O 错误带文件路径（JSON 损坏另带行号）返回错误，保留原文件。
  禁止把损坏统计视为零次；上下文构造失败产生失败运行，不让 LLM 静默继续。
- 终态记账先追加运行，再以副本提交健康状态到磁盘，成功后才更新内存及发布告警。
  写入失败跨帧重试；相同运行不会重复追加、增加失败次数或重复发布阈值告警。
- 每次运行失败通知一次，连续失败达到 `HARNESS_SCHEDULE_FAILURE_ALERT_THRESHOLD`
  （默认 3）时额外告警一次；处于告警状态后的第一次成功记录恢复并通知一次。
- 未完成记账或仍待发送回执的任务树不会因保留期清理。一次性定义等待持久记账完成后删除；
  过期的一次性定义也等待 `Missed` 落盘。定义持久化失败即使没有新状态变化也会重试。
- 运行中断后仍沿用 P0 的一次性任务暂停与提醒语义。待回执及待提交状态只在当前进程保留，
  不承诺跨重启重放外部发送；进程崩溃造成的半条 JSON 记录需要修复后再继续记账。

## 运行上下文与管理

- 自动附加 `<schedule-context>`，包括触发来源、触发时间、业务状态目录与通知策略。
- 最近 24 小时统计由 `ScheduleStore::run_summary` 读取账本生成，包含总数、通知、静默、
  失败、重叠跳过及错过次数；`report_of` 额外提供被观察任务的状态目录、上次成功、
  连续失败数、告警状态与区间统计。
- `schedule_task` / `update_scheduled_task` 支持 `notify`、`report_of`；后者的 `null`
  清除关联，不提供字段则保持原值。引用不存在的任务或自身时整条写效果失败，不部分更新。
- `list_scheduled_tasks` 返回策略、关联与健康字段。独立统计 API 可按 schedule 与起始时间查询。

## 验证范围

- 存储：结果持久化、时间窗、重复重试与已有重复行、末行无换行、坏 JSON、截断与 I/O 错误。
- 记账：终态幂等、真实回执等待、自动回复与显式通知成功 / 失败、健康写入失败重试、
  每次失败通知、阈值只告警一次与成功恢复一次。
- 触发及生命周期：策略和上下文注入、健康报告、损坏统计拒绝执行、重叠与过期留痕、
  过期账本失败重试、一次性定义等待记账、任务保留期保护。
- 检查：Markdown、格式、模块依赖、状态写入边界、全目标全功能 Clippy、全功能测试。
  平台发送由真实 ChannelManager 加可控测试 Channel 验证，未使用真实 QQ 账号发送验收消息。

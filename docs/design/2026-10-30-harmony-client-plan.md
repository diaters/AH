## 服务端接入设计

新增平台无关的 `client` 通道，未来其他平台复用协议。鸿蒙作为第一种客户端。

客户端接入模块同时提供两个角色：

1. 原生 Frontend：接收结构化引擎事件，提交任务输入、控制、审批和回答。
2. Channel Adapter：接入 `channel_send`、定时结果、附件和通知投递回执。

网络层负责鉴权、协议、传输和同步；运行时负责业务状态与执行。
不要把所有能力编码成聊天文本，也不要直接向远程客户端暴露内部 ECS 数据结构。

初步源码入口（恢复时核对当前版本）：

| 入口 | 调查所得与接入意义 |
| --- | --- |
| `src/domain/frontend.rs` | `EngineEvent`、`Frontend`、`UserAction`、`ChannelId` |
| `src/channels/traits.rs` | 消息、附件、通道接口、投递回调 |
| `src/channels/frontend.rs` | 现有 IM 事件文本转换；忽略工具开始等部分事件 |
| `src/channels/manager.rs` | 通道装配、收发监督、`send_with_result` |
| `src/channels/config.rs` | 通道配置与环境变量展开 |
| `src/systems/frontend_input.rs` | 前端动作进入统一输入链路 |
| `src/systems/frontend_output.rs` | 引擎状态输出、定时回复的特殊投递路径 |
| `src/systems/command.rs` | `/stop`、`/finish` 等现有控制语义 |
| `src/systems/conversation.rs` | 会话归属与输入顺序 |
| `src/domain/task.rs` | Task、审批关联、用户问答等待状态 |
| `src/domain/loop_control.rs` | steer 收件箱、后台任务与进程归属 |

当前广播事件也不能直接转发给远程设备，必须先按用户权限和任务归属过滤。

## 连接、配对和身份

- 实例拥有稳定 ID，可配置局域网地址与 EasyTier 地址；切换地址必须核对实例身份。
- 使用 HTTPS/WSS。明确证书信任方案，不使用关闭证书校验的方式连接。
- 新设备通过短时、一次性配对码／二维码配对，取得独立设备凭证。
- 配对确认展示实例身份；提供设备列表、凭证撤销与失效处理。
- EasyTier 解决可达性，不替代应用鉴权。
- 用户身份、会话 ID、设备 ID 分离。同一用户的手机和平板可访问同一会话。
- 服务端根据凭证确定操作者；不信任客户端自报的用户身份。
- 检查现有前端输入中的“本地可信操作者”路径，远程客户端不能继承 TUI 的可信旁路。
- 本地令牌使用系统安全存储，服务端避免记录凭证或带敏感正文的完整请求。

## 同步与命令协议

| 能力 | 合约要求 |
| --- | --- |
| 能力协商 | 返回协议版本与实际支持的操作；未支持功能不展示可点击操作 |
| 初始同步 | 会话、任务、待处理请求、自动化等快照与一致的事件游标 |
| 增量事件 | 事件 ID、序号、对象版本、关联任务；断线可补发 |
| 历史超出保留范围 | 明确要求重新同步快照，不能静默漏事件 |
| 控制命令 | 命令 ID、目标任务／会话、预期版本、结构化处理结果 |
| 幂等 | 同一命令重试不重复创建任务或审批；明确重启后的未决命令语义 |
| 文件 | 受授权的附件 ID、上传、预览和下载；不提供任意本地路径读取 |
| 回执 | 接收、持久化、执行／处理、通知投递、客户端收到、已读分别表达 |

- 快照与订阅之间不得有丢事件窗口。
- 服务端持久化会话记录和必要事件，明确历史保留范围及损坏后的报错策略。
- 离线输入保留草稿或待发送状态；普通发送重试复用命令 ID。
- 停止、审批等时效操作在重连后重新校验，禁止静默执行过期命令。
- 高频日志有批量、背压、截断标识和缺失范围；不能挤掉审批、错误和终态事件。
- 任务已结束后不接纳迟到控制，迟到执行结果继续遵守现有生命周期保护。

## 客户端信息结构与交互

采用 ArkTS、ArkUI、Stage 模型，工程目标为 API 26。

| 主入口 | 内容 |
| --- | --- |
| 会话 | 会话列表、任务状态、发起工作、历史搜索 |
| 自动化 | 定时任务、持续监控、后台进程及运行记录 |
| 收件箱 | 待审批、待回答、告警、恢复通知和未读结果 |
| 设置 | 实例、设备配对、连接、通知偏好和显示设置 |

任务工作区包含对话、进度、执行、产物四个视图。
默认呈现用户可理解的进展和结果，工具参数、日志、子任务详情按需展开。
内部推理不作为展示目标；没有真实依据时不生成进度百分比。

| 当前窗口空间 | 布局 |
| --- | --- |
| 窄窗口 | 单栏导航：会话列表、对话、详情逐级进入 |
| 中等窗口 | 会话列表＋对话双栏，详情侧面板 |
| 宽窗口 | 会话列表＋对话＋任务详情三栏 |

折叠／展开、横竖屏和分屏时保留当前会话、任务、草稿、上传状态、滚动位置和审批反馈。
布局变化不能重建任务、重复发送消息或重复建立业务订阅。

关键行为：

- 每个会话保持一个活跃顶层任务；多个会话支持并行工作。
- 运行中输入作为 steer，明确显示接收与排队状态，不能伪称 Agent 已消费。
- 新话题通过新会话发起，不把当前会话的运行中输入意外路由成新任务。
- “停止本轮”“结束任务”“停止进程”区分范围，复用运行时真实语义。
- 不展示尚无可靠恢复能力的“暂停／继续”按钮。
- 审批和问答绑定请求 ID／问题 ID；多设备处理后及时失效，服务端再校验。
- 审批选项来自服务端；点击通知后先刷新再操作，不能批准过期请求。
- 工具展示调用者、开始、结果与错误；子任务展示归属、进度和实际状态。

## 自动化与通知

- 定时任务支持查看、创建、编辑、启停和运行记录；展示规则、时区、下次运行和健康状态。
- 定时状态修改复用既有统一修改入口，并通知 timer scheduler、完成持久化。
- 持续监控／后台进程展示所属任务、最近输出、退出原因及可用操作。
- 运行链路为：计划触发、实际执行、运行结果、通知投递、客户端确认。
- 执行失败、通知失败、重叠跳过、错过运行和失败恢复分别呈现。
- 前台通过 WSS 同步；重要通知由服务端投递到 MeoW；回到应用后补齐完整状态。
- 重要通知包括审批、待回答、完成、失败和监控异常／恢复；普通工具进度不逐条推送。
- 持久化待投递内容与尝试记录，处理重启、超时、失败、恢复和每日 3000 条额度。
- 日界线与额度统计范围需明确；按配置时区计算，多个发送实例的统计边界需说明。
- 通知状态至少区分待投递、MeoW 返回成功、失败、结果未知、客户端收到、已读。
- 任务执行完成与通知完成分开记录；不能让任务无限等待用户打开客户端。
- 既有定时和监控回执链路必须覆盖新 channel，不得只增加一条无法追踪的旁路 HTTP 调用。

## 建议开发顺序

各阶段是实施顺序，不是将后续阶段取消；每个阶段完成实际验证后继续。

1. __服务端接入基础__：通道注册、配置、TLS、配对鉴权、设备撤销、能力协商；
   明确身份、会话和设备模型，接入 headless 与统一输入链路。
2. __会话与可靠同步__：持久化快照、事件、幂等命令和补发；
   完成任务发起、steer、停止／结束、审批、问答和基础附件的端到端闭环。
3. __鸿蒙原生工作区__：手机、平板、阔折叠布局同时完成，接入真实服务端；
   完成草稿、重连、错误、过期请求与多设备同步，避免用静态假数据冒充功能。
4. __运行观察与自动化__：子任务、待办、工具结果、进程输出、产物；
   接入定时任务管理、健康、运行账本和通知记录。
5. __MeoW 自动通知__：配置、投递队列、结果、重试、额度、通知策略和跳转验证；
   通过实际任务触发并收集用户接收确认，不能只重复手动 curl 测试。
6. __管理与诊断__：模型／provider 状态、真实可获得的用量、Skills、记忆、权限审计、实例诊断；
   依据服务端能力开放操作，保留授权、错误反馈与审计。
7. __整体验证与交付__：自审、仓库必需检查、原生构建和真机验证、提交与 PR。

如发现已有机制可直接复用，优先复用，不为每一项新增独立抽象。
新增依赖必须满足仓库的 crates.io、许可证、跨平台和真实需求约束。

## 验证与交付门槛

自动化重点验证行为：

- 未配对、失效令牌、设备撤销、跨用户任务／文件访问被拒绝。
- 同一输入重试、请求并发、进程重启不重复创建工作；未知状态可查询或明确返回。
- 快照与增量同步无间隙，事件去重、游标过期、慢客户端与存储损坏可诊断。
- 运行中输入归属正确，停止／结束不误伤其他会话，迟到操作不影响新任务。
- 两台设备同时处理审批只有一次有效；过期请求拒绝；问题回答绑定原请求。
- 文件权限、大小限制、失败恢复；日志高流量不阻塞关键事件。
- 定时修改真正影响调度；执行账本与 MeoW 投递结果分别记录。
- MeoW 的 HTTP／业务失败、限流、超时未知、重试重复风险与每日额度处理。

仓库必需检查：

```sh
bash scripts/check_module_deps.sh
bash scripts/check_status_assignment.sh
cargo fmt --all --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
```

另外执行仓库配置对应的 Markdown 检查及鸿蒙工程构建／静态检查。
自动化通过不代替真机验收。

真机至少验证手机、平板或阔折叠，包含折叠展开、分屏、前后台、锁屏、进程回收、
Wi-Fi／EasyTier 切换、断网重连、多设备审批、附件和实际通知接收。
记录提交、设备、系统／API 版本、步骤、预期和实际结果；必要验证未完成时不得合入。

按仓库规则使用功能分支与 PR；创建 PR 后立即启用 auto-merge，不能绕过必需 CI。
若仍有必要人工验证，使用草稿和明确阻塞条件，避免在验证前变为可合并状态。
合并后确认独立提交已进入 main 或等价，再清理分支与临时 worktree。

## 更换服务器后的启动步骤

1. 获取本计划及功能分支；确认目标服务器仓库、分支、基线、工作区差异和 `AGENTS.md`。
2. 使用 CodeGraph 查询结构；若未初始化，按仓库要求先询问是否运行 `codegraph init -i`。
   当前机器的索引存在文件列表与 checkout 不一致的迹象，具体编辑以目标 Git 文件为准。
3. 检查 Rust、Cargo、Node、Git、GitHub 身份和网络，运行合适的基线检查。
4. 明确构建拓扑：Linux 等服务器开发／测试 Rust 服务端；
   鸿蒙客户端需要支持的 DevEco／API 26 构建环境与可连接设备，必要时分机协作。
5. 安装／定位真实 API 26 SDK 与匹配工具，不修改 SDK 元数据伪装为 API 26，
   不把 API 20 构建描述为 API 26 验证。
6. 部署局域网／EasyTier 可达地址、证书和设备信任；配置 MeoW 昵称与每日额度。
   不迁移或提交 `.env.local` 等密钥，使用必要的配置示例说明。
7. 恢复开发前说明本次目的、影响范围、行为变化和验证计划，然后按上面顺序推进。

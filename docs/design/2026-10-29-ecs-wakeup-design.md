# ECS 按需唤醒与负载治理方案

> __状态：当前有效（已确认的实施设计）__。用户于 2026-10-29 确认方案。
> 实现状态：已落地并通过本地全量验证（2026-10-30）。改造前源码分析基线：`2f69b90`。
> 长期记忆时间规则已单独确认；当前能力以 [current-state](../current-state.md) 为准。

## 目标与结论

建议保留 Rust + Bevy ECS、现有七段 `HarnessSet` 和异步执行桥，将运行方式改成：

- 外部输入、执行结果与回执到达时唤醒。
- ECS 连续处理当前可推进的工作；只有等待外部条件或未来时间时才休眠。
- 超时、重试与维护按最近截止时间唤醒。
- 热路径按受影响实体处理，TUI 按可见变化刷新。

这是调度机制调整，不新增 Task / WorkItem 类型、不改变 Agent 权限、不扩展 LLM 工具面。
设计评审已通过，实施与验证记录见配套计划；未验证的目标不视为已实现能力。
以下性能判断来自源码路径，尚未采样实际 CPU，也没有可宣称的实测降幅。

## 改造前负载证据（2f69b90）

| 位置 | 已确认行为 | 影响与处理方向 |
| --- | --- | --- |
| `src/app/run_loop.rs::run_loop` | 每轮无条件 `app.update()`，随后 sleep | 没有事件也执行调度图 |
| `src/systems/runtime_config.rs` | 默认 active 16 ms、idle 150 ms | 忽略执行耗时，约 62.5 / 6.7 次每秒 |
| `src/app/mod.rs::app_is_idle` | 扫描 Task 和多类消息，任何非终态任务都不算 idle | 等用户、LLM、审批也会保持 active |
| `src/main.rs::TuiLoop` | `!idle` 时重绘，终端输入以零超时轮询 | 等待态仍反复渲染 |
| `src/systems/ingress.rs::retry_wakeup_system` | 每轮遍历所有 Task 查重试时间 | 可改成重试截止时间唤醒 |
| `src/systems/tools/waiting.rs` | 完成事件处理与每轮全量等待检查并存 | 重复检查 waiter 的目标列表 |
| `src/systems/tools/cancel_monitor.rs` | 每个在飞调用线性查找父任务 | 最坏接近在飞调用数 × Task 数 |
| `src/systems/sweeper.rs` | 每轮扫描在飞调用的时间 | 可按到期调用处理 |
| `src/systems/memory.rs` | 每轮遍历长期记忆并修改分数 | 既有扫描成本，也有频率影响业务语义的问题 |
| `src/systems/schedule.rs` | 每轮检查运行、回执与待落盘项，失败跨帧重试 | 需要回执唤醒和有间隔的持久化重试 |
| `src/systems/loop_control/monitor.rs` | 输出采集已限频，但回执和待投递批次每轮检查 | 采集、合并窗口、重试需要分别唤醒 |

已有优化应继续使用：

- `terminal_task_retention_system` 与 `conversation_idle_system` 已有 30 秒扫描间隔，
  不能把它们的全量树遍历算成每 16 ms 一次。目标是让未到期时无需为了调用它们而跑 ECS。
- `background_job_monitor_system` 已受 `background_poll_ms` 限频，属于待进一步事件化的后端轮询。
- `triggers/timer_scheduler.rs` 已使用 `tokio::select!` 等待下次触发或配置变化；
  无任务时有 60 秒等待。保留其 cron、一次性任务及本地时区语义，只补接主循环唤醒。
- 消息 Component、`PendingDispatch`、`EntityIndex`、所有权关系已有真实复用价值，继续作为基础。

## 备选方案

| 方案 | 收益 | 局限 | 结论 |
| --- | --- | --- | --- |
| 增大 active / idle 间隔 | 变更小、立即减少轮数 | 增大输入和结果延迟，轮内重复扫描仍在 | 仅可作为临时缓解 |
| 全面添加 `Changed<T>` / `run_if` | 可避免部分业务逻辑 | 主循环仍醒；`Changed<T>` 仍需检查匹配实体 | 作为局部工具 |
| 按需唤醒 + 截止时间 + 热路径定向处理 | 同时削减空转与无关遍历 | 必须补齐所有唤醒源和内部续跑 | 推荐 |
| 全面改成 actor 或 Observer 回调网络 | 可完全事件化 | 重写顺序、所有权和错误链路，审计成本高 | 当前不采用 |

Bevy 0.18.1 本地依赖源码 `src/query/filter.rs` 的 `Changed` 文档明确指出：
该过滤器不是 archetype filter，即便没有变化也会检查所有匹配实体。
因此它可以减少业务处理，却不能被当作“只访问变化实体”的性能保证。

## 推荐架构

```text
输入 / LLM / 工具 / 进程事件 / 发送回执 / 关闭信号
              │ 先保存数据，再发唤醒通知
              ▼
       有界、可合并的唤醒通道
              │
              ▼
主线程等待 ── 外部到达 / 最近截止时间 / 内部续跑
              │
              ▼
Ingress → Signal → Transform → Dispatch → Execution → Output → Maintenance
              │                                      │
              ├─ 还有可立即推进的工作：继续一轮       └─ 可见变化：刷新 TUI
              └─ 仅剩等待：进入阻塞等待
```

### 分离可运行、等待和关闭

- `Runnable`：输入、结果、到期计时、可执行请求或跨阶段后续工作需要处理。
- `Waiting`：业务未结束，但只等待 LLM、工具、用户、审批、子任务、回执或未来期限。
- `Quiescent`：当前无待推进工作，也无在飞业务；仍可保留历史实体及未来定时任务。

这三个词是调度分类，不增加三套实体生命周期状态机。
主循环依赖“是否存在可立即推进的工作”，不再依赖 Task 是否终态。
休眠资格与优雅退出资格必须分开：等待用户可以休眠，但不能因此被误判为满足现有关闭条件。
本方案保留首次信号等待、宽限期退出、第二次信号立即退出的产品语义。

### 最小唤醒桥

新增一个内部 `RuntimeWake` 能力，由 `app` 装配，低层契约供生产者使用。
优先复用已有 crossbeam-channel 的容量为 1 的通知通道；数据仍保存在现有业务通道中。
`try_send(())` 满时允许合并通知，绝不丢弃业务数据。
数据发送成功后再通知；发送失败走原错误路径。不要直接暴露可绕开通知的 sender 字段。

生产者接入清单：

- TUI / IM 的用户动作、`ExternalInput`，包括 timer 和 webhook。
- LLM 执行结果、模型链状态更新、异步工具结果与 effect 返回。
- 定时运行发送回执、持续输出发送回执，既含成功也含失败。
- shell 输出事件、进程退出、启动失败、主动停止和会话删除。
- 关闭信号，包括当前只递增原子计数、不发送 `Shutdown` 的第二次信号。
- 外部配置变更入口；纯 ECS 内部变更通过续跑机制推进。

`Frontend::poll_actions()` 当前是拉取契约，不能假设所有实现都会通知。
内置前端接入唤醒；暂不能通知的适配器必须显式登记有间隔的兼容轮询 deadline，
直到完成迁移。不能因补齐了 `ExternalInput` 就删除所有轮询。

主线程使用 `recv_deadline` / `recv_timeout` 等待通知或期限；无期限可阻塞 `recv`。
通知断开应进入明确的关闭或错误路径，不允许返回后立即循环形成忙等。
该等待能力见 [crossbeam-channel 0.5.15 官方文档][crossbeam-recv]。

防止丢唤醒的顺序：

- 一轮开始先取走已有通知，再排空或按预算消费各数据源。
- 一轮结束确认内部无可运行工作，然后等待；不可在该确认后无条件清空通知。
- 确认与阻塞之间到达的数据会留下通知，阻塞接收立即返回。
- 按预算留下的数据必须登记续跑；不能消费通知后留下数据却进入休眠。
- 允许空通知造成一次无害检查；禁止靠周期全图扫描补救漏通知。

### 内部推进与停止条件

保留七段集合顺序及既有 `.before/.after` 依赖，使用一个内部续跑标记记录有意义的后续工作。
不将 `Clock` 更新时间、统计变更、任意 `ResMut` / `Changed<T>` 当成业务进展。

- 生产请求、消息、待提交 effect 或状态迁移时，若消费者本轮已运行，登记下一轮。
- 首轮强制执行启动链路；启动系统产生的工作也必须进入同一续跑机制。
- 每轮开始取走并清除“本轮”标记；本轮产生的“下一轮”标记不得被结束逻辑覆盖。
- `Maintenance` 创建 Agent / 产生工具结果 → 下一轮 Transform / Dispatch 必须立即推进。
- `Maintenance` 修改定时定义 → 下一轮 Output 必须落盘，不能依赖新的外部输入。
- Pending 实体存在不等于可运行；缺 Agent、等审批、等回执时登记等待条件，不能永久续跑。
- 等待条件满足时只激活相关消费者；错误重试必须带未来 deadline，不能每轮立刻重试。

实施时逐一核对 Update 系统的输入、输出、跨集合依赖和等待条件，形成完整登记表。
首版可保留一轮必要的候选查询；不要求把所有系统改造成通用事件总线。
高成本系统再基于消息 Component、领域 dirty 集合或截止时间设置 `run_if`，
运行条件本身不能通过全表扫描来判断“是否该扫描”。

Bevy 的 `Commands` 延迟提交必须在消费者及休眠判定前可见。
沿用依赖边上的自动提交，收尾在 `app.update()` 返回后的已提交状态判断续跑；
不要手动直接调用 `ApplyDeferred` 函数冒充 schedule 同步点。

连续推进设置预算，初始建议每批最多 8 轮或约 4 ms，参数先作为内部常量验证。
预算只在系统之间检查，不能抢占正在执行的同步系统。
耗尽时处理关闭、输入和 UI，再继续待执行工作，不因预算耗尽丢工作或固定休眠。
每个输入源同样限批，避免持续输出或消息洪峰垄断主线程。

### 截止时间统一等待，业务调度保持原归属

增加进程内 `RuntimeDeadlines`，仅管理“什么时候需要再次处理”，不复制 `SchedulerState`。
可使用标准库 `BTreeMap` 按时间排序，并用键到当前期限的映射支持更新和撤销。
键为“原因 + Entity / 请求身份 / 全局维护项”；到期只生成候选，业务真相仍由 ECS 校验。

| 原因 | 注册 / 更新时机 | 唤醒后的处理 |
| --- | --- | --- |
| Task 重试 | 进入或修改 RetryBackoff | 生成既有重试 Signal |
| `wait_tasks` 超时 | 注册或替换等待 | 校验本次等待，产出一次结果 |
| 工具失联兜底 | 工具开始 / 完成 / 取消 | 保留 claim → ingest 单点落地 |
| 输出合并与重试 | 第一段输出 / 失败回执 | 沿用合并窗口、attempt 与顺序 |
| 定时账本和定义落盘重试 | 写盘失败 | 有上限间隔退避，成功后撤销 |
| 任务回收与会话清理 | 启动与上次维护完成 | 保留当前 30 秒维护粒度 |
| 长期记忆治理 | 启动、记忆变化与治理完成 | 采用独立的时间语义，见下节 |
| 临时后端轮询 | 不支持通知且确有活动对象 | 仅轮询该后端，再登记下次期限 |
| 关闭宽限期 | 第一次关闭信号 | 无其他事件也能按期退出 |

每个可替换请求携带 generation / attempt；同一实体开始新等待后，旧计时不能结束新等待。
完成、取消、删除同步撤销；到期消费再次校验实体有效性、状态和身份。
结构有界性由替换和删除保证，不无限保留失效堆项。

运行期相对等待使用单调时间；持久化时间与 cron 继续使用 UTC / 本地时区语义。
现有 `Clock` 测试注入能力必须保留，改造为可同时控制墙钟与单调时间的测试时钟。
旧 `next_retry_at` 等墙钟字段到运行期期限的投影规则必须在实施设计中明确，不能混算两种时间。
墙钟跳变校验可以作为低频 deadline，仅重算受影响的时间任务，不触发全业务扫描。

### 按受影响实体执行

| 链路 | 推荐改造 | 保留的不变量 |
| --- | --- | --- |
| 等待子任务 | 注册时检查现状；反向索引 child → waiters；完成时只检查相关 waiter | 完成与超时竞争只产出一次结果 |
| 工具取消 | 先复用 `EntityIndex` 消除父任务线性查找，再按 owner 组织调用 | `/stop`、终态与 owner 删除均触发取消 |
| 后台 shell | 后端在保存输出和最终状态后通知；退出时才读取通知尾部 | 所有权与 `notify_on_exit` 语义不变 |
| 记账 | 终态、输出派发、回执或重试到期只激活对应 run | 真实回执计数、落盘成功后结束 |
| 短期记忆压缩 | STM 写入、压缩结束、相关 WorkItem 状态变化标脏 | 保留现有压缩阈值和互斥条件 |
| 前端展示 | 收到 EngineEvent / 输入 / resize 才标记重绘 | 审批、状态和最终文本不会漏显示 |

反向索引只是可重建的派生数据，必须在登记、替换、完成、取消与销毁处同步维护。
沿用现有 ECS 所有权关系；没有关系才增加最小索引，不建立第二套 Task 状态数据库。
初始化只允许一次重建；日常复杂度应与活跃对象及受影响对象相关，而非历史 Task 总数。

改造前长期记忆存在独立正确性问题：每次在旧 `decay_score` 上减去由完整年龄算出的惩罚，
并加上重要度和复用奖励；相同时间连续调用也可能重复改变分数。
因此必须先独立评审并修正时间语义，再切换主循环，不能只把该系统改为每分钟调用。
推荐按实际经过时间衰退、访问和复用通过独立状态更新产生影响；明确基准分数、评估时间、
旧持久化记录的迁移规则与 pin / Critical 豁免。具体公式另立任务，不在本方案中暗改遗忘策略。
验收必须包含同一墙钟时刻重复执行幂等，以及相同时间跨度不同执行次数结果一致。

### TUI 与 ECS 分离

使用专用终端输入线程阻塞等待事件，事件入队后唤醒主线程；ratatui 绘制仍由主线程负责。
只能由该线程读取 crossterm 事件，保留按键种类过滤、粘贴、鼠标、resize 与错误处理。
线程用有界超时检查退出标记以便 join；这只是输入线程等待，不触发 ECS 更新。

`LoopHooks` 拆清楚输入处理、待绘制状态和下次动画期限。
纯输入框编辑、滚动及动画只触发 UI；提交任务或审批才触发 ECS。
同批 ECS 输出在绘制前消费，避免现有“下一轮 poll 才看见”的额外延迟。
有变化时限制最大刷新率；静止时不重绘；动画或耗时显示使用独立 deadline。
headless 不安装 UI timer，heartbeat 改按时间低频记录，不按 300 帧计数。

## 实施拆分与兼容性

- 第一批：建立基线与系统触发清单，补全唤醒 sender，保持现有驱动验证通知覆盖。
  同时独立修正长期记忆时间语义、父任务重复查找；不急于删除旧驱动。
- 第二批：迁移截止时间、存储失败退避与内部续跑，补齐 TUI 输入和所有关闭路径。
  在通知、期限和续跑契约全部验证后，切换生产主循环为阻塞等待。
- 第三批：根据负载数据迁移 waiters、取消、后台进程、记账与压缩热路径，删除重复轮询。
  每条路径切换时同步移除旧消费路径，避免重复结果和两套逻辑长期并存。

不新增 crate。保持 ECS 单写者，异步 worker 仍只返回数据。
新类型按既有依赖方向归属 contracts / infrastructure / systems / app，禁止低层引用 app。
正式切换后，`HARNESS_ACTIVE_POLL_MS` / `HARNESS_IDLE_POLL_MS` 不再作为 ECS 调度参数；
建议保留一个兼容窗口，检测到显式设置时告知已废弃及新行为，不悄悄改成另一个含义。
届时同步 `configuration.md`、`.env.example`、README、current-state 和 pipeline 文档。
`background_poll_ms` 仅在兼容轮询尚存时保留原含义，全部后端迁移后再统一退役。

## 验证与验收

### 正确性门槛

- 用同步屏障在“检查结束、尚未阻塞”处注入输入 / 工具结果 / 回执，验证不会漏唤醒。
- 唤醒合并、批处理限额、多数据源并发时，每条业务数据仍被处理一次。
- 无外部输入时，Maintenance 生成的 Agent、effect 结果、定时定义变更仍能自行处理完。
- 仅有等待用户、审批、LLM 的任务时允许休眠；输入、取消、结果到达立即恢复推进。
- 使用假时钟验证重试、wait 超时、工具兜底、合并窗口、回执重试、维护和关闭宽限期。
- 同帧完成与超时、取消与迟到结果、实体删除及复用、旧 attempt 回执都不重复完成。
- 用已有定时任务 P1 用例验证一次性任务不会提前删除，待回执与待记账树不会提前回收。
- 两次关闭信号均能唤醒，且 TUI 退出可回收输入线程。
- 对照同一输入序列，旧 / 新驱动的用户输出、工具效果、审批和持久化结果一致；
  长期记忆仅允许发生独立确认过的语义修正。

### 性能测量

先用 release 构建、mock executor / channel 和固定实体夹具采集基线，避免网络延迟掩盖差异。
比较同一机器、同一实体集的旧 / 新驱动；报告重复运行的中位数及 P95 / P99 延迟。

| 场景 | 核心观察 |
| --- | --- |
| headless 无任务，60 秒 | ECS 更新次数、线程 CPU 时间、唤醒次数 |

记录 `ecs_update_count`、各热系统执行及访问实体数、`tui_draw_count`、唤醒原因、deadline 延迟、
队列高水位和预算耗尽次数。聚合统计，避免逐实体 debug 日志成为新的负担。

结构性验收目标：

- 稳态无事件时 ECS 更新次数只对应实际到期维护，不再由 16 / 150 ms 定时器决定。
- 静止且无动画的 TUI 绘制次数为零；第二次关闭信号不依赖下一次轮询。
- 在基线明确后，以空闲 / 等待场景 CPU 时间下降至少 80% 为初始目标；
  若原始值接近测量噪声，报告绝对 CPU 时间与唤醒次数，不用失真百分比验收。
- 热路径检查量以受影响对象为主；单事件端到端延迟 P95 不劣于原基线，
  同时记录 P99，排除通过积压工作换取低 CPU 的情况。

这些是待实施验收目标，不是本轮实测结果。
